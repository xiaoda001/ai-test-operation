# 工程决策记录

> 每做一个"为什么这么做/不做"的判断就记一条。面试讲"工程判断力"的素材库——
> 不是背结论，是能讲清当时的取舍背景。格式：背景 → 选项 → 决定 → 理由。

## D1 · Day 4：多轮历史为什么放前端，不放后端

- **背景**：Day 4 要实现多轮对话，历史可以放前端 state，也可以放后端 session。
- **选项**：A 前端维护完整 messages / B 后端按 session_id 维护。
- **决定**：Day 4 先用 A，Day 5–6 再演进到 B。
- **理由**：
  1. 教学透明——验收要求"打印 messages 数组在增长"，放前端能亲眼看到"LLM 无状态、每轮重发全量"这个本质；
  2. 最小改动——Day 2 的 `/chat` 签名不用动；
  3. 留学习内容——session_id、持久化是 Day 5–6 主线，一次做完没得学且会被细节淹没。
- **关键认知**："谁持有历史"和"发给模型什么"是两件事——无论历史存哪，发给模型的都是完整 messages。

## D2 · Day 4：为什么现在不封装 SSEStore

- **背景**：Day 2 之后设计过一个 SSE 客户端库（按 id 缓存 fullText、自动组装增量、多订阅者）。
- **决定**：Day 2、Day 4 都不动手，只记录设计；Day 5 多会话出现时再封装。
- **理由**：封装时机由真实需求驱动——
  - Day 2：一条流、一个组件，缓存和 id 匹配毫无价值；
  - Day 4：单会话，一个 messages 数组够用；
  - Day 5：多会话、多气泡并发流式更新，"每帧更新哪个气泡"成为真问题，id 路由从锦上添花变刚需。
- **原则**：重复真实出现 ≥2 处、或 state 硬扛不住时才抽抽象。过早抽象 = 为假想需求设计。

## D3 · Day 2：SSE 上游报错为什么选"保留异常并中断"

- **背景**：流式开始后 HTTP 200 已发出，无法改回 500，错误只能在帧层面表达。
- **选项**：A 异常冒泡、连接断、不发 `[DONE]` / B 自定义 error 帧再补 `[DONE]`。
- **决定**：Day 2 选 A，B 留到 Day 20 失败兜底阶段引入。
- **理由**：Day 2 核心是验证流式链路跑通；`[DONE]` 语义是"正常说完"，出错硬发是撒谎。
  错误处理分阶段引入更干净，且两个方案面试都能讲。

## D4 · Day 2：前后端连接为什么选"浏览器直连 + CORS"

- **背景**：选项 A Next.js rewrite 代理 / B 浏览器直连后端 + 后端 CORS。
- **决定**：选 B。
- **理由**：
  1. 直连让 curl 和浏览器走同一条路，流式出问题一眼定位；
  2. SSE 经中间代理有被 buffer 的真实风险，学习阶段不引入不确定性；
  3. CORS 是面试高频点，顺手配会；
  4. 与最终前后端分离部署（K8s）形态一致，不用中途推翻。

## D5 · Day 4：system prompt 为什么外置 + 后端强制插入

- **背景**：system prompt 可硬编码在代码里，也可放模板文件；client 可传 system 消息。
- **决定**：抽成 `backend/app/prompts/hook_analysis.txt`，后端每次请求读取并置顶，过滤客户端传来的 system。
- **理由**：
  1. 改提示词不改业务代码；
  2. 防注入——否则用户发 `role=system` 的消息就能覆盖应用规则；
  3. 配合 `response_format=json_object` 双保险，输出可解析（Day 16 Agent 工具调用的地基）。

## D6 · Day 4：可观测性为什么自研，不上 Langfuse

- **背景**：现成 LLM 观测平台一次给全套能力（trace/成本/评测/回放）。
- **决定**：自研轻量版——SQLite + `track_llm_call` 中间件 + `/traces` 接口。
- **理由**：面试会追问"每个字段怎么来的"，用第三方平台答不上来。自研几百行，字段全自己定义，
  且复用"按 id 缓存"的思路（从内存缓存演进为持久化 trace）。
- **技术要点**：流式必须用 `stream_options={"include_usage": True}`，否则 chunk 里没有 usage。
